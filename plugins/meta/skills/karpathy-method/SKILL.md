# Метод Карпати — рабочий стандарт фабрики

Это не философия для красоты. Это чек-лист, по которому агенты фабрики создаются, работают и прокачиваются. Если сомневаешься, как делать — делай по этому методу.

## Три уровня софта (рамка мышления)

Карпати делит софт на три поколения, и агент должен понимать, на каком уровне работает:

- **Software 1.0** — обычный код, который человек пишет явными инструкциями.
- **Software 2.0** — веса нейросети, «запрограммированные» данными.
- **Software 3.0** — программа на естественном языке. LLM — это интерпретатор, а **контекстное окно — это твоя программа**. То, что лежит в контексте (промпт, спека, примеры, инструменты), И ЕСТЬ код агента.

Вывод для фабрики: агента мы «программируем» не кодом, а его определением — системным промптом, спекой задачи и набором скиллов/инструментов. Поэтому качество агента = качество его контекста.

## Пять принципов (применять всегда)

### 1. Контекст — это программа
Прежде чем запускать агента, спроси: всё ли нужное лежит в контексте и ничего ли лишнего? Урезай шум. Плохой результат почти всегда — это плохой контекст, а не «глупая модель». Спека задачи (что сделать, критерии приёмки, ограничения) — главный артефакт. Нет спеки — нет работы.

### 2. Держи петлю короткой
Агент действует циклом: **прочитал окружение → принял решение → сделал шаг → проверил результат → поправил**. Не пиши простыни «сделай всё сразу». Дроби на маленькие проверяемые шаги. Чем короче цикл «действие → проверка», тем меньше накопленная ошибка.

### 3. Eval-driven: всё измеримо
Никакой работы без критерия «готово». У каждой задачи должна быть проверка: тест, чек-лист, эталон, автоматическая верификация. Если награду/результат нельзя проверить — сначала придумай, как проверять, потом делай. Прогресс без метрики — это иллюзия прогресса.

### 4. Человек в петле, автономия — постепенно
Не строй сразу полностью автономную махину. Сначала агент предлагает — человек подтверждает. По мере роста доверия (и накопленных метрик) отпускай поводок. «Ползунок автономии» двигается на основании данных, а не веры.

### 5. Разделяй роли: пишет — критикует — проверяет
Сильный результат даёт не один гений-агент, а конвейер: один драфтит, другой критикует, третий гоняет тесты. Разные роли (и по возможности разные модели) ловят ошибки, которые один агент пропускает. Это прямо ложится на структуру отделов фабрики.

## Как применять при СОЗДАНИИ агента

1. Сформулируй одну чёткую цель агента (одно предложение). Размытая цель → размытый агент.
2. Опиши спеку: входы, выходы, критерии приёмки, чего агент НЕ делает.
3. Дай минимально достаточный набор инструментов. Лишние инструменты = лишний шум и риск.
4. Заложи проверку результата (как поймём, что агент отработал хорошо).
5. Начни с узкой версии 0.1, а не с «универсального солдата». Расширяй по данным.

## Как применять при АПГРЕЙДЕ агента

1. Собери фидбэк из `agents/<отдел>/<агент>/feedback.md` — реальные проколы, а не догадки.
2. Найди узкое место: плохой контекст? нет проверки? слишком широкая цель?
3. Внеси МИНИМАЛЬНОЕ изменение, которое чинит конкретный прокол.
4. Зафиксируй в `agents/<отдел>/<агент>/changelog.md` что и зачем поменяли, бампни версию.
5. Не переписывай агента целиком из-за одного бага. Маленькие проверяемые правки.

## Красные флаги (стоп-сигналы)

- «Сделай всё и сразу» без разбивки на шаги.
- Задача без критерия «готово».
- Агент с десятком инструментов «на всякий случай».
- Апгрейд «переписал заново, стало лучше» без замера.
- Контекст, забитый нерелевантным мусором.

Если видишь красный флаг — остановись и вернись к принципам.
